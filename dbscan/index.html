k-means asks you how many clusters there are and then insists every point belongs to one of them. DBSCAN asks neither. It asks how crowded a neighborhood has to be to count as a cluster, and everything too far from a crowd is left out as noise. The number of clusters is whatever falls out.

Two knobs do all the work: a radius \(\varepsilon\) and a count \(minPts\).

Core, border, noise

Points \(p\) and \(q\) are neighbors when they are within \(\varepsilon\) of each other, so the neighborhood of \(p\) is

\[N_\varepsilon(p) = \{\, q \in D : \lVert p - q \rVert \le \varepsilon \,\}\]

and note \(p \in N_\varepsilon(p)\) — a point is its own neighbor. That convention matters because \(minPts\) counts it. Three roles follow:

RoleConditionWhat it does
core\(|N_\varepsilon(p)| \ge minPts\)Sits inside a dense region. Pulls its whole neighborhood into its cluster.
bordernot core, but \(p \in N_\varepsilon(q)\) for some core \(q\)Joins \(q\)'s cluster and stops there. Contributes nothing of its own.
noiseneitherBelongs to nothing. Reported as an outlier.

The asymmetry between core and border is the whole algorithm. A cluster grows by hopping from core point to core point through overlapping neighborhoods, and a border point is absorbed without being allowed to expand. Drop that restriction and a single thin trail of sparse points would let two clusters leak into each other. Keep it and the trail dead-ends.

Formally, \(q\) is directly density-reachable from a core point \(p\) when \(q \in N_\varepsilon(p)\); density-reachable is the transitive closure of that over core points; and a cluster is a maximal set of mutually density-connected points — pairs that are both density-reachable from some common core point. Less formally: run a flood fill and refuse to flood out of a non-core cell.

The algorithm, as two passes

Scan the points in order. Every point not yet reached seeds a breadth-first search. Pop a point, count its neighbors, and if it is core, claim it for the current cluster and queue its unvisited neighbors. If it is not core, mark it undetermined and queue nothing. That is pass one.

Pass one cannot finish the job, because a non-core point popped early might still be inside some cluster discovered later. So pass two sweeps the undetermined points once more: any of them with a core neighbor becomes a border point of that cluster, and the rest are noise.

pass 1:
  for each point p in index order:
    if p already reached: skip
    BFS from p:
      pop x; n = |N(x)|
      if n >= minPts:  label[x] = current cluster;  queue x's unreached neighbors
      else:            label[x] = undetermined;    queue nothing

pass 2:
  for each undetermined p:
    label[p] = cluster of p's first core neighbor, else noise

Two details are arbitrary but worth pinning down so the output is reproducible: cluster ids follow discovery order from index 0, and a border point reachable from two clusters joins its lowest-indexed core neighbor's. Every DBSCAN implementation makes some choice here, and the choice is only ever visible on border points sandwiched between clusters.

Watching it run

Hollow gray points have not been looked at yet. A white ring means queued but not yet popped — that is the BFS frontier. The highlighted point is the one being examined right now, with its \(\varepsilon\) disc drawn and lines to each neighbor it can see. Amber hollow points are undetermined, waiting for pass two. Filled points are clustered: large discs are core, small ones border. A gray cross is noise.

The faint lines inside a finished cluster are the density-connectivity edges, drawn only where at least one endpoint is core. They are the paths the flood fill was allowed to travel, which is a more honest picture of what DBSCAN found than a blob outline would be.

Hover any point to inspect it: its neighbor count, its role, and its \(\varepsilon\) disc, at any stage of the run.

Choosing ε

\(minPts\) is the easier of the two. It is a minimum cluster size and a noise-tolerance dial at once: bigger means fewer, denser, more conservative clusters and more points written off as noise. A common starting point is \(minPts \approx 2d\) for \(d\)-dimensional data, so 4 in the plane, nudged up when the data is noisy.

With \(minPts = k+1\) fixed, \(\varepsilon\) has a graphical answer. A point is core exactly when its \(k\)-th nearest neighbor is within \(\varepsilon\). So compute that distance for every point, sort descending, and plot it. Points inside clusters have small \(k\)-distances and form the long flat tail; outliers have large ones and form the steep rise on the left. The knee between them is the natural \(\varepsilon\): below it you start carving clusters apart, above it you start swallowing noise.

Drag the \(\varepsilon\) slider and watch the horizontal line sweep across this curve while the scatter plot above recounts its core points. The relationship is exact, not a heuristic: every point below the line is core.

Where it breaks

DBSCAN has one global \(\varepsilon\), which means it assumes one global density. Switch the data to varying density and the assumption bites. There is no single radius that resolves the tight blob and the loose blob at the same time: tune \(\varepsilon\) for the dense one and the sparse one dissolves into noise, tune it for the sparse one and the dense one merges with whatever is near it. This is precisely what OPTICS and HDBSCAN were built to fix, by considering a whole range of radii instead of one.

The second weakness is dimensionality. Neighborhood counts stop discriminating as \(d\) grows — distances concentrate, every point ends up roughly equidistant from every other, and no \(\varepsilon\) separates dense from sparse. Reduce first, cluster second.

Cost is the friendlier story. The work is dominated by the neighborhood queries, one per point, and everything else is bookkeeping. Brute force makes each query \(O(n)\) for \(O(n^2)\) total, which is what the code above does and what the animation replays. Put the points in a k-d tree or ball tree and the average case drops to \(O(n \log n)\). Memory stays \(O(n)\): there is no \(n \times n\) distance matrix, unlike agglomerative clustering.

Things to try

Run the two moons and the concentric rings. Both are trivial here and both are impossible for k-means, because DBSCAN never assumes a cluster has a center — it only follows density. Then set the data to uniform and watch what happens when there is no structure at all: at small \(\varepsilon\) everything is noise, at large \(\varepsilon\) everything is one cluster, and in between the algorithm invents clusters out of random fluctuations in the sample. Density-based clustering will always find something, so the shape of the \(k\)-distance curve is worth checking before you trust the output.

For the pass-two behaviour, drop the speed to a few steps per second on blobs + noise and watch the amber points. Most turn blue as border points; the leftovers become crosses. If you want to see the tie-break rule matter, find an amber point sitting between two clusters and note which one claims it.

Also worth doing: set \(minPts\) to 1. Every point becomes core, nothing is ever noise, and DBSCAN degenerates into single-link connected components at threshold \(\varepsilon\) — which is the same thing as cutting a single-linkage dendrogram at height \(\varepsilon\). The two families meet at that corner. For the wider map of which family assumes what, there is the four families of clustering.
